# Правила проекта

## 1. Продуктовые правила

### 1.1 Источник идентичности пользователя

Приоритет источников identity:

1. Telegram `initData`
2. `user_id` из явного запроса
3. `username`
4. подписанная cookie-сессия

Если `user_id` недоступен, допустим browser fallback по `username`, но только как режим совместимости.

### 1.2 Регистрация гостя

- Гость считается зарегистрированным только если в `Список гостей` подтверждение участия выставлено в truthy-значение.
- В `Список гостей!F` canonical идентификатором считается `user_id`; `username` допустим только как временный compatibility fallback.
- При следующей успешной регистрации с валидным Telegram identity существующая username-based запись должна быть переведена на numeric `user_id`.
- Поиск гостя должен уметь работать как по `user_id`, так и по `username`.
- Telegram-идентификатор в проекте является бизнес-ключом доступа к личным сценариям.
- Дополнительные гости создаются отдельными строками, но логически принадлежат владельцу основной регистрации.
- Отмена регистрации владельца должна снимать подтверждение со всех строк, связанных с его идентификатором.

### 1.3 Игры и очки

Текущие правила начисления:

- `dragon`: `200` игровых очков = `1` рейтинговое очко
- `flappy`: `2` игровых очка = `1` рейтинговое очко
- `crossword`: `1` успешное действие = `25` рейтинговых очков
- `wordle`: `1` отгаданное слово = `5` рейтинговых очков

Ранги рассчитываются только от суммарного рейтингового счёта.

### 1.4 Рассадка

- В Mini App доступны два представления: опубликованная версия рассадки по столам и персональный просмотр своего стола.
- Источник истины для показа гостю — `Рассадка_фикс`, который админ обновляет из текущего листа `Рассадка`.
- Сопоставление гостя с опубликованной рассадкой не должно ломаться из-за перестановки имени и фамилии местами.
- Рабочий лист `Рассадка` после синхронизации нормализуется автоматически: внутри каждого стола сначала идут подтверждённые (`TRUE`) гости, затем неподтверждённые (`FALSE`), и каждая группа сортируется по алфавиту.
- В рабочем листе `Рассадка` заливка ячейки определяется по `родству` из `Список гостей!D`, а цвет текста — по `стороне` из `Список гостей!E`.

### 1.5 Фото и видео

- Все фото и видео из чата и Mini App должны сходиться в одну папку Google Drive.
- Лист `Фото` хранит метаданные загрузки, а не бинарное содержимое файла.

## 2. Инженерные правила

### 2.1 Конфигурация и секреты

- Не коммитить реальные токены, credentials и локальные env-файлы.
- Работать через `.env.local` локально и через переменные окружения в проде.
- Любое новое обязательное env-поле должно быть отражено в `.env.example` и `README.md`.

### 2.2 Frontend pipeline

- Исходники фронтенда живут только в `webapp-react/`.
- Deployable bundle живёт в `webapp/`.
- После изменения фронтенда, если проект разворачивается из текущего репозитория без отдельного CI-пайплайна на frontend, нужно пересобрать `webapp/`.

### 2.3 Google Sheets как контракт

- Нельзя менять смысл колонок молча.
- Любое изменение схемы листов должно сопровождаться обновлением документации.
- Если добавляется новый лист, его нужно либо создать через `EnsureRequiredSheets`, либо явно описать как внешний ручной артефакт.

### 2.4 Обработка ошибок

- Публичный API должен возвращать единый JSON-формат ошибок.
- Критические ошибки инфраструктуры должны быть логированы и, при необходимости, отправлены админам.
- Не использовать панику как штатный механизм бизнес-логики.

### 2.5 Производительность

- Частые чтения из Google Sheets нужно по возможности кэшировать.
- Негативный кэш использовать осторожно, чтобы не ломать свежие подтверждения гостей.

## 3. Правила разработки

### 3.1 Любое изменение должно отвечать на один из вопросов

- улучшает пользовательский сценарий;
- уменьшает риск инцидента;
- упрощает поддержку;
- подготавливает следующий функциональный шаг.

### 3.2 Обязательные проверки перед публикацией

Минимальный набор:

- `go test ./...`
- `go build ./cmd/server`
- `cd webapp-react && npm run build`

Если какая-то проверка не проходит из-за внешнего окружения, это нужно явно зафиксировать в итоговом отчёте.

### 3.3 Приоритет изменений

Порядок приоритета:

1. корректность данных гостей и identity;
2. стабильность игровых сценариев;
3. админские операции;
4. визуальные улучшения;
5. необязательная оптимизация.

### 3.4 Работа с долгом

Если в коде есть TODO в уже активном пользовательском сценарии, он получает более высокий приоритет, чем новый декоративный функционал.

## 4. Операционные правила

### 4.1 Прод-эксплуатация

- `DEBUG=false`
- корректно настроены `BOT_TOKEN`, `GOOGLE_SHEETS_ID`, credentials и `WEBAPP_URL`
- бот должен иметь доступ к нужной группе, если используется проверка членства

### 4.2 Деплой

- Собранный frontend должен соответствовать текущему backend API.
- Нельзя деплоить изменения схемы данных без проверки совместимости с текущими листами.

### 4.3 Наблюдаемость

- Важные ошибки должны быть видны в логах без доступа к IDE.
- Любая новая фоновая задача должна быть идемпотентной или защищённой от повторного запуска.
